## 1. Reusable deployment template — `template_01.yml`

Save this as `template_01.yml`, or use its contents to replace your current reusable template.

```
parameters:
  - name: airflow_bucket
    type: string
  - name: gcp_secure_file
    type: string
  - name: deployment_environment
    type: string

steps:
  # GCP AUTHENTICATION
  - task: DownloadSecureFile@1
    name: google_credentials
    inputs:
      secureFile: '${{ parameters.gcp_secure_file }}'
    displayName: 'Download GCP Service Account Key'

  - script: |
      set -euo pipefail
      chmod 600 "$(google_credentials.secureFilePath)"
      gcloud auth activate-service-account --key-file="$(google_credentials.secureFilePath)"
    displayName: 'Authenticate with GCP'

  # DEPLOY CHANGED DAG AND PLUGIN FILES
  - script: |
      set -euo pipefail

      BUCKET_URI="gs://${{ parameters.airflow_bucket }}"
      ENVIRONMENT="${{ parameters.deployment_environment }}"
      DEPLOY_COMMIT="$(git rev-parse HEAD)"
      STATE_URI="$BUCKET_URI/_deployment_state/$ENVIRONMENT/last_successful_commit.txt"

      case "$ENVIRONMENT" in
        sandbox|test|prod) ;;
        *)
          echo "ERROR: Unsupported deployment environment: $ENVIRONMENT"
          exit 1
          ;;
      esac

      CHANGES_FILE="$(mktemp)"
      STATE_FILE="$(mktemp)"
      trap 'rm -f "$CHANGES_FILE" "$STATE_FILE"' EXIT

      echo "Environment: $ENVIRONMENT"
      echo "Target bucket: $BUCKET_URI"
      echo "Deployment commit: $DEPLOY_COMMIT"

      # READ THE LAST SUCCESSFULLY DEPLOYED COMMIT
      if BASE_COMMIT="$(gcloud storage cat "$STATE_URI" 2>/dev/null | tr -d '\r\n')" && [[ -n "$BASE_COMMIT" ]]; then
        echo "Last successfully deployed commit: $BASE_COMMIT"

        if ! git cat-file -e "${BASE_COMMIT}^{commit}" 2>/dev/null; then
          echo "ERROR: The previous deployment commit is unavailable in Git history."
          echo "Cannot safely calculate the deployment changes."
          exit 1
        fi
      else
        echo "WARNING: No deployment checkpoint exists for $ENVIRONMENT."
        echo "Using an empty Git tree for the initial deployment."

        BASE_COMMIT="$(git hash-object -t tree /dev/null)"
      fi

      # DISABLE RENAME DETECTION: RENAMES BECOME DELETE + ADD
      # -z PRESERVES FILENAMES CONTAINING SPACES OR NEWLINES
      git diff --name-status --no-renames -z \
        "$BASE_COMMIT" "$DEPLOY_COMMIT" -- DAGS/ plugins/ > "$CHANGES_FILE"

      # DELETE AN OBJECT, TOLERATING AN ALREADY-ABSENT OBJECT
      delete_object() {
        local uri="$1"

        if gcloud storage ls "$uri" >/dev/null 2>&1; then
          echo "Deleting: $uri"
          gcloud storage rm "$uri" --quiet
        else
          # Confirm the bucket is accessible before treating the object as absent.
          gcloud storage ls "$BUCKET_URI/" >/dev/null
          echo "INFO: Object is already absent: $uri"
        fi
      }

      PROCESSED_COUNT=0

      # PARSE NUL-DELIMITED GIT STATUS/PATH PAIRS
      while IFS= read -r -d '' status; do
        if ! IFS= read -r -d '' file_path; then
          echo "ERROR: Incomplete Git change record."
          exit 1
        fi

        case "$file_path" in
          DAGS/*)
            target_folder="dags"
            relative_path="${file_path#DAGS/}"
            ;;
          plugins/*)
            target_folder="plugins"
            relative_path="${file_path#plugins/}"
            ;;
          *)
            continue
            ;;
        esac

        target_uri="$BUCKET_URI/$target_folder/$relative_path"

        case "$status" in
          D)
            delete_object "$target_uri"
            ;;
          A|M|T)
            source_file="$(Build.SourcesDirectory)/$file_path"

            if [[ ! -f "$source_file" ]]; then
              echo "ERROR: Source file does not exist: $source_file"
              exit 1
            fi

            echo "Uploading: $file_path -> $target_uri"
            gcloud storage cp "$source_file" "$target_uri"
            ;;
          *)
            echo "ERROR: Unsupported Git status '$status' for $file_path"
            exit 1
            ;;
        esac

        PROCESSED_COUNT=$((PROCESSED_COUNT + 1))
      done < "$CHANGES_FILE"

      if (( PROCESSED_COUNT == 0 )); then
        echo "No changed DAG or plugin files detected."
      else
        echo "Successfully processed $PROCESSED_COUNT changed files."
      fi

      # UPDATE THE CHECKPOINT ONLY AFTER ALL FILE OPERATIONS SUCCEED
      printf '%s\n' "$DEPLOY_COMMIT" > "$STATE_FILE"
      gcloud storage cp "$STATE_FILE" "$STATE_URI"

      echo "Deployment checkpoint updated: $DEPLOY_COMMIT"
    displayName: 'Deploy Changed DAG and Plugin Files'
```

### What the new template does

It compares the current commit against a checkpoint stored separately for each environment:

```
gs://<bucket>/_deployment_state/sandbox/last_successful_commit.txt
gs://<bucket>/_deployment_state/test/last_successful_commit.txt
gs://<bucket>/_deployment_state/prod/last_successful_commit.txt
```

This prevents a deployment from relying exclusively on `HEAD~1`. If a deployment fails partway through, its checkpoint is not advanced, so the next run can retry the changes.

Initial deployment warning: if no checkpoint exists, the template uses the empty-tree hash and uploads the currently tracked DAG and plugin files. It does not automatically delete old GCS files that were removed from Git before that initial checkpoint existed. Check existing bucket contents and establish a suitable baseline before rolling this out to an existing TEST or PROD bucket.

## 3. Before running the updated pipeline

There are four things to verify.

1\. Configure PR validation in Azure DevOps. If this repository is Azure Repos Git, go to Repos → Branches → `main` → Branch policies → Build Validation and make this pipeline a required validation build. Also configure the required reviewer approvals. The YAML `pr:` block alone does not trigger PR validation for Azure Repos Git.&#x20;

2\. Configure deployment locks. In each Azure DevOps environment—`Sandbox - Airflow DAGS`, `Test - Airflow DAGS` and `Prod - Airflow DAGS`—add an Exclusive lock check. The `lockBehavior: sequential` setting then makes runs queue sequentially for that protected resource.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn



3\. Validate the initial deployment checkpoint. Before running against existing TEST or PROD buckets, confirm how their current contents correspond to Git history. A missing checkpoint causes the template to upload all currently tracked DAGs and plugins, but it will not automatically clean up files that were deleted from Git before the checkpoint was created.

4\. Correct the environment variables before real promotion. In the supplied configuration, every stage points to the same sandbox bucket. The TEST and PROD stages would therefore modify the sandbox bucket too. Use the verified, separate bucket names and service-account keys before enabling genuine promotion. Until then, run only controlled validation and avoid concurrent pipeline runs.

### Recommended test sequence

| Test                                       | Expected result                                                         |
| ------------------------------------------ | ----------------------------------------------------------------------- |
| PR contains changes across several commits | Change report detects all changes relative to the target branch.        |
| Add or modify a DAG/plugin                 | Only the changed file is uploaded.                                      |
| Delete a DAG/plugin                        | Its GCS object is removed.                                              |
| Rename or move a file between folders      | Old object is removed; new file is uploaded to the correct destination. |
| Introduce an Airflow DAG import error      | Validation fails, so deployment stages do not run.                      |
| Force a deployment operation to fail       | The environment checkpoint remains unchanged.                           |
| Run successive deployments                 | Each environment compares against its own last successful deployment.   |

One final note: the updated code checks DAG import errors using Airflow's `DagBag` in the TEST image. Confirm that the image and its configuration support parsing your DAGs in this isolated test environment; DAGs that require external services or metadata during module import may need test fixtures or mocks.
