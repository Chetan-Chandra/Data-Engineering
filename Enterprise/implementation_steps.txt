Phase 4 — GCS bucket IAM

This is where you need to be careful.

Your existing Canam GKE workload identity uses:

sa-kubtogcp@prj-n-cdp-ingestion.iam.gserviceaccount.com

Your sandbox could technically reuse that service account, with bucket-level permissions added only to the sandbox bucket.

However, for proper environment isolation, I recommend:

sa-kubtogcp-sandbox@prj-n-cdp-ingestion.iam.gserviceaccount.com

rather than reusing the TEST identity.

Google recommends Workload Identity Federation for GKE for fine-grained workload access rather than service-account keys.

Sandbox GCP service account

Create:

sa-kubtogcp-sandbox

Then give it only the permissions that sandbox Airflow actually requires.

For the Airflow DAG bucket, the exact role depends on how your GCS FUSE CSI configuration accesses the bucket.

At minimum, if Airflow needs to read objects:

roles/storage.objectViewer

If Airflow itself needs to create/update/delete objects:

roles/storage.objectAdmin

Do not automatically give project-wide Storage Admin.

Grant access at the bucket level.

For example:

gcloud storage buckets add-iam-policy-binding \
  gs://bkt-prj-n-cdp-ingestion-airflow_dag-sandbox \
  --member="serviceAccount:sa-kubtogcp-sandbox@prj-n-cdp-ingestion.iam.gserviceaccount.com" \
  --role="roles/storage.objectAdmin"

And similarly for logs if your Airflow design requires direct GCS access.

The principle should be:

Sandbox service account
        │
        ├── READ/WRITE → sandbox DAG bucket
        │
        └── READ/WRITE → sandbox log bucket

and not:

Sandbox service account
        │
        └── Storage Admin → entire project

Phase 7 — Sandbox Airflow metadata database

This is an item you did not explicitly mention, but it is critical.

Airflow needs its metadata database.

Your existing environment has:

Cloud SQL
prj-n-cdp-ingestion:northamerica-northeast1:airflow-postgres

Do not point sandbox Airflow at the TEST Airflow metadata database.

Otherwise you could have:

TEST Airflow
       │
       ▼
same Airflow metadata DB
       ▲
       │
Sandbox Airflow

That is not isolated.

You have two good designs.

Option A — Separate Cloud SQL database

Same Cloud SQL instance:

airflow-postgres
      │
      ├── airflow_test
      │
      └── airflow_sandbox

This is the cheaper option.

Option B — Separate Cloud SQL instance
airflow-postgres-test
airflow-postgres-sandbox

This provides stronger isolation but costs more.

For a sandbox, I'd generally start with:

same Cloud SQL instance + separate Airflow database/schema, assuming your organization's operational/security requirements allow it.

But the sandbox must have its own Airflow metadata database, not merely its own DAG bucket.

Phase 10 — Artifact Registry IAM

You need two different access patterns.

Azure DevOps

Your CI/CD identity needs permission to push the sandbox image.

Prefer:

roles/artifactregistry.writer

on the sandbox repository rather than broad project-wide Artifact Registry Admin.

Artifact Registry supports repository-level IAM, and Google specifically recommends configuring permissions at the repository level when appropriate.

GKE

The GKE workload/node identity needs permission to pull the image.

Typically:

roles/artifactregistry.reader

on the repository.

So:

Azure DevOps
     │
     └── Artifact Registry Writer
                  │
                  ▼
          airflow-sandbox
                  ▲
                  │
     Artifact Registry Reader
                  │
                  GKE

Phase 16 — Azure DevOps secure files

and uploading its key only if your current Azure DevOps authentication design still requires service-account keys.

The most important things you were missing

You already identified most of the visible pieces. The main things I'd add are:

1. Sandbox Airflow metadata DB

This is mandatory for true isolation.

2. Sandbox GCS log bucket

Don't share TEST logs.

3. Sandbox Kubernetes namespace

Don't just create another bucket while running the same Airflow deployment.

4. Sandbox Kubernetes ServiceAccount

Don't reuse TEST identity unnecessarily.

5. Sandbox GCP service account

Prefer a dedicated identity.

6. Sandbox Artifact Registry repository/image

Correctly identified by you.

7. Sandbox Airflow Helm release

The UI must actually point to the sandbox resources.

8. Sandbox DNS/Ingress

Otherwise you'll still be accessing TEST UI.

9. Sandbox secrets/connections

Particularly SQL Server, Oracle, RabbitMQ, Snowflake, etc.

10. Sandbox Pub/Sub/Snowpipe path

If you want to test the complete ingestion pipeline rather than only DAG execution.

11. Terraform representation

The sandbox infrastructure should ultimately be managed consistently with the existing Canam infrastructure.

12. Network connectivity

The sandbox Airflow pods still need connectivity to whatever sources they are supposed to test—SQL Server, Oracle, RabbitMQ/CloudAMQP, Snowflake, etc. A new namespace/bucket doesn't automatically give the pods network access.

One architectural recommendation

Don't try to build all of this simultaneously.

Use these three milestones:

MILESTONE 1
Sandbox Airflow infrastructure
        ↓
Sandbox UI works
        ↓
Manual DAG works

Then:

MILESTONE 2
Azure DevOps
        ↓
Sandbox Docker image
        ↓
Sandbox GCS deployment
        ↓
DAG appears in Sandbox UI

Then:

MILESTONE 3
Complete pipeline
        ↓
GCS
 ↓
Pub/Sub
 ↓
Snowpipe
 ↓
Snowflake sandbox

That separation will make troubleshooting dramatically easier.
