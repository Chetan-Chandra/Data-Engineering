```text
Pub/Sub

   ↕
Azure Event Hubs
   ↕
```

That will become one of our biggest themes.

# 19. Example: Why Your Architecture Uses GCS

Interviewer:

> Why didn't you load directly from SQL Server into Snowflake?

Your architect reasoning should become:

```text
Source
 ↓
GCS
 ↓
Snowflake
```

because GCS gives us:

### Decoupling

Source extraction doesn't depend directly on Snowflake availability.

### Replayability

Raw files can be reprocessed.

### Durability

We preserve source data independently.

### Multi-consumer capability

Other systems can consume the raw data.

### Cost separation

Storage and compute have different characteristics.

### Auditability

We can retain original ingestion artifacts.

### Schema evolution

Raw data can be retained even if downstream schemas change.

Now you've answered as an architect.

---

# 20. Example: Why Airflow?

Don't say:

> "Airflow schedules pipelines."

Instead:

> Airflow provides orchestration and dependency management across heterogeneous data-processing tasks. In our architecture it coordinates extraction, ingestion and transformation workflows, handles retries and scheduling, provides operational visibility, and allows dependencies to be expressed as a DAG.

Then immediately:

> "But Airflow isn't the data-processing engine itself."

That distinction is important.

---

> "Terraform creates infrastructure."

# 28. Where We Start

We should **not start with Spark or Kafka**.

Your first lesson should be:

# **Module 1 — Data Architecture Fundamentals & Architect Thinking**

And we'll build it around your actual project.

The first thing we'll establish is:

```text
Data
 ↓
Data Architecture
 ↓
Data Platform
 ↓
Data Pipeline
 ↓
Data Engineering
 ↓
Data Architecture Decision
```

Then we'll take your existing:

```text
SQL Server → Python → GCS → Pub/Sub → Snowpipe → Snowflake → dbt → BI
```

and dissect it **box by box**:

> **Why is this component here?**

> **What requirement does it satisfy?**

> **What happens if we remove it?**

> **What alternatives exist?**

> **Why did we choose it?**

> **How would we scale it from 1 GB/day to 10 TB/day?**

> **How would we make it secure?**

> **How would we make it highly available?**

> **How would we monitor it?**

> **How would we implement the same architecture on Azure?**

> **How would we implement it using Databricks/Kafka?**

> **What would change and what would remain conceptually identical?**

That will be our **Data Architect training loop**.

And one more thing: your current project should remain the **golden reference project**, rather than becoming a collection of disconnected demos. Every new technology will either **extend it, replace one component temporarily for comparison, or be demonstrated as a small isolated experiment**. That keeps the learning aligned with the Genpact role and prevents us from spending weeks on tool-specific trivia.
